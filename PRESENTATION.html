Background and Problem Statement

Problem identified

Academic records managed across separate spreadsheets and manual processes create:

  • Duplicate data entry — student details captured in multiple places with no single source of truth
  • Inconsistent records — marks, enrolment status, and course assignments updated independently, leading to mismatches
  • No structured academic tracking — quarterly marks, averages, and pass/fail status calculated manually without validation
  • No role-based access — administrators, lecturers, and students share the same uncontrolled access to all data

These problems were assumed for the purpose of this prototype to demonstrate a working solution. The system was developed as an internship assessment project, not deployed into a live departmental environment.

Proposed solution

A web-based Student Portal System that centralises academic data in a relational database, enforces business rules in PHP application logic, and provides role-based interfaces for administrators, lecturers, and students.

Implementation and Code Quality

OOP design decisions

  • Encapsulation — All class attributes are private. External access goes through getters and setters only
  • Separation of concerns — RegistrationService handles student number generation and multi-step registration logic, separate from the Student entity class
  • Static finder methods — Each entity class provides findById(), getAll(), and domain-specific lookups (e.g. findByStudentNumber())
  • Business rules in PHP — Enrollment validates single-active-enrolment. ModuleResult validates mark ranges 0-100. RegistrationService checks for duplicate emails and student numbers
  • Transactions — Student registration uses beginTransaction() / commit() / rollBack() to ensure student record, user account, and enrolment are created atomically

Security measures implemented

  • All SQL queries use PDO prepared statements with bound parameters
  • Passwords hashed with password_hash() (bcrypt) and verified with password_verify()
  • Session-based authentication with role checks on every protected page
  • Input sanitisation with filter_var() and trim()
  • Output encoding to prevent cross-site scripting

Example: Mark validation (ModuleResult.php)

public static function validateMark(
    ?float $mark, string $field = 'Mark'
): void {
    if ($mark === null) return;
    if ($mark < 0 || $mark > 100) {
        throw new InvalidArgumentException(
            "{$field} must be between 0 and 100. 
             Value provided: {$mark}"
        );
    }
}

Example: Average calculation

public function calculateAverage(): ?float {
    $marks = array_filter(
        [$this->quarter1, $this->quarter2, 
         $this->quarter3, $this->quarter4],
        fn($val) => $val !== null
    );
    if (count($marks) === 0) return null;
    $this->average = round(
        array_sum($marks) / count($marks), 2
    );
    return $this->average;
}

Known limitations

Challenges, Limitations and Future Improvements

Challenges faced

  • Many-to-many relationships — Designing the course-module and module-lecturer junction tables and writing the correct JOIN queries took the most design time
  • Backward compatibility — The original database had a flat students table. Normalising it while keeping old columns working required dual mappings in the Student class constructor
  • Student number uniqueness — Initial implementation could generate duplicates under concurrent inserts. Fixed with a loop-until-unique database check
  • Transaction integrity — Registration involves three database operations (student, user, enrolment). Had to wrap in a transaction to prevent partial records on failure

Current limitations

  • No automated testing framework — all testing was manual
  • No CSRF protection on forms
  • No audit trail for data modifications
  • No file upload capability (e.g. student photos)
  • No email notifications for registration or mark updates
  • Single-server deployment, no horizontal scaling

Slide 15

Conclusion

Problem addressed

The Student Portal System replaces fragmented, manual academic record-keeping with a centralised web application. Student records, course enrolments, module assignments, quarterly marks, and academic performance are stored in a single relational database and accessed through role-based interfaces.

Technical achievement

  • 9 PHP classes with encapsulated attributes and separated responsibilities
  • 8 MySQL tables with foreign keys, junction tables, and integrity constraints
  • 3 role-based interfaces (admin, lecturer, student) with session-based authentication
  • Business rules enforced in both PHP and MySQL: single active enrolment, mark validation (0-100), unique student numbers, duplicate prevention
  • Transactional registration creating student, user, and enrolment records atomically
  • All database queries use PDO prepared statements

Lessons learned

  • Designing the database correctly before writing code saved significant rework
  • Business rules belong in the application logic, not just in the user interface
  • Backward compatibility adds complexity but prevents breaking existing data
  • Manual testing is useful but insufficient — automated tests are a clear next step
